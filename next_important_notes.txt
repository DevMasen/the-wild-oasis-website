1. PROJECT OVERVIEW
=================================

- Purpose: Next.js hotel-booking frontend ("The Wild Oasis") for browsing luxury
  cabins, viewing cabin details, picking reservation dates, and managing a guest
  account/profile. Built while working through Jonas Schmedtmann's Ultimate
  React course (commit subjects E422-E467 map to course exercises).
- Current implementation status: functional reading/browsing features are in
  place; the write/booking flow is only partially wired (reservation form
  renders but has no submission handler; reservations page shows a hard-coded
  empty list; profile form inputs are disabled). Treat it as a course project
  in progress, not a production app.
- Next.js version: 14.2.35 (App Router, pages under app/).
- React version: ^18, plain JavaScript (no TypeScript). jsconfig.json sets the
  "@/*" alias to the repo root.
- Main technologies: next, react, react-dom, @supabase/supabase-js, date-fns,
  react-day-picker, @heroicons/react, tailwindcss, prettier-plugin-tailwindcss.
- Styling: Tailwind with a custom primary/accent palette (tailwind.config.js),
  global CSS at app/_styles/globals.css.
- Data: Supabase (PostgreSQL backend) accessed from server components only
  through a client singleton at app/_lib/supabase.js. Environment variables are
  NOT NEXT_PUBLIC, so they stay server-side (per AGENTS.md).
- Routing: Next.js App Router (file-system routes in app/). No pages/ directory,
  no API routes, no Route Handlers, no Server Actions in the current code.
- Verified by reading current source; git history confirms the incremental
  course-exercise progression. No test framework is installed
  (AGENTS.md: verification = lint then build).

3. CORE CONCEPTS AND IMPLEMENTATIONS
=================================

3.1 App Router and file-system routing
- Routes are defined by folders/files in app/: page.js = route UI,
  layout.js = shared UI, loading.js = loading UI, error.js = error UI,
  not-found.js = 404 UI. Bracketed folders like [cabinId] are dynamic routes;
  the segment is received as params.cabinId.
- Nested layouts: app/account/layout.js wraps account pages and adds a sidebar
  without reloading on navigation between /account, /account/profile,
  /account/reservations.
- Linking: next/link is used everywhere (Navigation, CabinCard, Logo). It
  enables client-side navigation without full page reloads. Anchor <a> tags
  were replaced by Link over history (e.g. CabinCard, SideNavigation commits).

3.2 Server vs Client Components
- Default: server components. Data fetching happens on the server (Supabase
  calls in page components), so secrets never reach the browser and pages can
  be prerendered.
- "use client" is added only when interactivity or browser APIs are needed:
  Filter (router/useSearchParams), DateSelector (useState via context +
  DayPicker), TextExpander (useState toggle), UpdateProfileForm (useState),
  SideNavigation (usePathname), ReservationContext (createContext/useState).
- Client components can be nested inside server components and receive props
  (CabinList inside cabins/page, Reservations inside [cabinId]/page, Filter
  inside cabins/page). Boundaries are explicit and deliberate, not
  "everything is a client component."
- ReservationProvider is a client component placed at the root layout so
  range state can be shared between DateSelector and ReservationForm without
  lifting state to a shared server ancestor.

3.3 Data fetching
- All fetching is async/await directly in server components/pages; no
  useEffect data fetching, no SWR/React Query.
- Data layer is centralized in app/_lib/data-service.js. Each function wraps a
  Supabase call, logs + throws on error (getCabin additionally calls
  notFound()). Examples:
    export async function getCabins() {
      const { data, error } = await supabase
        .from("cabins").select("id, name, maxCapacity, regularPrice,
          discount, image").order("name");
      if (error) { console.error(error); throw new Error("..."); }
      return data;
    }
- getCabin returns a single record (.single()) and calls notFound() on error,
  which Next.js converts to the route's not-found UI.
- Commented-out setTimeout delays remain in data-service.js (e.g. in getCabin,
  getCabins, getCabinPrice, getSettings) as testing hooks for loading states.
- getCountries is the only non-Supabase fetch, hitting an external REST API;
  its query field changed from name,flag to name,x (commit 55b5f1f fix), and
  the comment references a future server action that does not exist.

3.4 Rendering strategies: SSR, ISR, SSG
- Server components render on request by default (SSR-like).
- ISR via export const revalidate:
    cabins/page.js: revalidate = 3600
    about/page.js:  revalidate = 86400
  These are cached and regenerated in the background after the interval.
- SSG via generateStaticParams() in app/cabins/[cabinId]/page.js:
    export async function generateStaticParams() {
      const cabins = await getCabins();
      return cabins.map(c => ({ cabinId: String(c.id) }));
    }
  Prerenders all cabin detail pages at build time. Note: getCabins runs both
  at build (for params) and at request time (in the page), which is a minor
  duplication worth knowing.
- Dynamic metadata via export async function generateMetadata({ params }) in
  [cabinId]/page.js, returning { title: `Cabin ${name}` }. The root layout
  also exports a static metadata object with a title template.

3.5 Streaming and loading states
- React Suspense with fallback={<Spinner />} splits the page into streaming
  units:
    cabins/page.js: <Suspense key={filter}><CabinList /></Suspense>
    [cabinId]/page.js: <Suspense><Reservations /></Suspense>
- The key={filter} on the cabins Suspense boundary forces a remount when the
  filter changes, so new data is fetched for the new filter value.
- Route-level loading.js files: app/loading.js (whole app) and
  app/cabins/loading.js (/cabins and [cabinId] segment). Originally
  app/cabins/page.js had its own loading UI; it was moved into a dedicated
  loading.js (commit E448/E445) to leverage Next.js automatic loading UI.
- Loading states are immediate (spinner shown while Suspense boundary
  suspends); there is no artificial delay in production code, only commented
  test delays.

3.6 Error handling
- app/error.js: client error boundary for unexpected errors. Receives { error,
  reset }; clicking "Try again" calls reset() to retry the failing boundary.
- notFound() in getCabin (data-service.js) triggers 404 handling:
    app/not-found.js (root), app/cabins/[cabinId]/not-found.js (segment-level).
- Errors thrown in data-service are caught by the nearest error boundary;
  getBookings/getSettings/etc. throw generic "could not be loaded" errors.

3.7 Forms, state, mutations
- No Server Actions. No <form action={...}>. ReservationForm and
  UpdateProfileForm are plain client components with uncontrolled inputs and
  buttons that currently do nothing on submit. Mutations exist in
  data-service.js (createBooking, updateBooking, deleteBooking, createGuest,
  updateGuest, deleteBooking) but are not called from any UI component.
- Client-side state: useState in TextExpander, UpdateProfileForm, Counter;
  useReservation context for date range; useSearchParams/useRouter/usePathname
  in Filter and SideNavigation.
- URL as shared state: the cabin capacity filter lives entirely in the URL
  (?capacity=small). Filter reads useSearchParams and calls router.replace to
  mutate the query string without reloading. cabins/page reads
  searchParams.capacity as a server prop and passes it down. This commits
  filter state to the URL so it is shareable and survives refreshes.

3.8 Images and fonts
- next/image for all images: remote cabin images from Supabase storage
  (requires images.remotePatterns entry in next.config.mjs for the
  ecqqdmjyrtkkceyczkve.supabase.co host), static imports for local public
  images (bg.png, logo.png, about-1.jpg), and fill/object-cover for
  responsive cover images.
- Fonts: Josefin_Sans from next/font/google with subsets: ["latin"] and
  display: "swap", applied to <body> in layout.js. Self-hosted, eliminates
  layout shift.

3.9 Authentication / authorization
- No real auth. getGuest(email) looks up a guest by email (Supabase) and
  deliberately does not throw when missing ("We handle the possibility of no
  guest in the sign in callback" comment), but there is no sign-in page or
  session handling. SignOutButton is a static button. ReservationForm renders
  "Logged in as" with commented-out user image/name. Treat auth as not
  implemented.

5. KEY TECHNICAL DECISIONS
=================================

- App Router, no pages/: follows Next.js 14 conventions; layouts, loading,
  error, and not-found UI are file-based. Verified in app/ structure.
- Central server data layer (_lib/data-service.js + _lib/supabase.js): keeps
  Supabase logic out of components, makes reuse (getCabins used by cabins,
  about, [cabinId]) and testing delays easy to manage.
- Server components by default, client only where needed: avoids shipping
  interactivity to the browser unnecessarily; keeps Supabase keys server-side
  (env vars are not NEXT_PUBLIC).
- next/image for every image (remote allow-list in next.config.mjs): automatic
  optimization, but remote hosts must be listed or builds fail.
- URL-based filter state (?capacity): persists filters, makes them linkable,
  avoids a global state library.
- Suspense + streaming: cabin page shell renders immediately while the slower
  Reservations component streams in, improving perceived performance.
- notFound() in getCabin: declarative 404 without try/catch in the page.
- Reverted output: "export": shows static export was considered but does not
  fit a dynamic, server-data-driven app; next.config.mjs no longer has it.
- @/* alias (jsconfig.json): absolute imports like "@/app/_lib/data-service"
  instead of relative paths.

Trade-offs / caveats:
- generateStaticParams runs getCabins at build AND the page calls getCabin at
  request time; if cabin data changes after build, metadata/params may be stale
  until rebuild or revalidation.
- Client components nested in Suspense boundaries: ReservationForm/DateSelector
  are client but rendered inside a server Suspense boundary — valid, but the
  boundary suspends on the server-side data they depend on (Reservations is
  async server component).
- No Server Actions: mutations (createBooking etc.) exist in data-service but
  are not invoked from any form, so booking cannot actually be completed.

6. COMMON PITFALLS AND LESSONS
=================================

1. Missing next/image remote host -> build failure.
   Evidence: next.config.mjs images.remotePatterns lists only the Supabase
   storage host; it was added in commit E445,446 right when remote cabin
   images were introduced. Any new image host must be added here.

2. "use client" placement matters.
   Evidence: Filter, DateSelector, TextExpander, UpdateProfileForm,
   SideNavigation, ReservationContext all declare "use client" at the top.
   Forgetting it breaks hooks (useState/useSearchParams/usePathname) in
   components that need them; overusing it moves data fetching to the client.

3. notFound() vs throwing.
   Evidence: getCabin calls notFound() on Supabase error; getBookings/
   getSettings throw. notFound() is the correct way to surface a 404 in server
   components; throwing produces a 500/error-boundary instead.

4. Static export is not compatible with this app.
   Evidence: commit E456 added output: "export" and commit 94ba550 removed it.
   Do not re-add without confirming the app no longer needs dynamic server
   data.

5. Env var names are server-only.
   Evidence: app/_lib/supabase.js reads process.env.SUPABASE_URL and
   process.env.SUPABASE_API_KEY. They must be defined in .env.local and are
   not exposed to the browser because they lack the NEXT_PUBLIC_ prefix.
   Never hardcode or log these values.

6. Filter key={filter} remounts Suspense boundary.
   Evidence: cabins/page.js wraps CabinList in <Suspense key={filter}> so
   changing the capacity filter refetches data. Removing the key would reuse
   the boundary and could show stale data.

7. Commented-out setTimeout delays.
   Evidence: multiple functions in data-service.js contain
   // await new Promise((res) => setTimeout(res, 2000));. They are test hooks,
   not production delays; leaving them commented is intentional but easy to
   miss when debugging slow loads.

8. Incomplete write flow.
   Evidence: ReservationForm submit button, DeleteReservation, and
   UpdateProfileForm have no handlers; reservations page hard-codes
   bookings = []; data-service mutation functions are defined but never
   called. Do not assume booking/profile updates work.

9. Auth comments can be misleading.
   Evidence: getGuest says missing guest is handled in "the sign in
   callback", but no sign-in callback/UI exists. SelectCountry's comment
   mentions splitting values "later in the server action", but no server
   action exists. Treat such comments as roadmap notes, not implemented
   behavior.

Routing constraints:
  Dynamic segment [cabinId] is passed to pages as params.cabinId.
  Search params (?capacity) are read as page props (searchParams) in server
  components and via useSearchParams in client components.

Server/client boundary pitfalls:
  - Hooks and event handlers only in "use client" components.
  - Supabase client must be instantiated and used in server components only.
  - A client component cannot directly import and call async server data
    functions unless those functions are Server Actions (none exist here);
    data should be fetched in a server ancestor and passed down as props.
